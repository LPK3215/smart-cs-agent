# 6. 定向产出 · 面试准备

> 目的：基于第 3/4 步，产出「技术细节 + 难点 + 我的解决方案表述 + 选型考虑」问答稿。
> 适用于"AI 应用工程师 / LLM 全栈 / 智能体开发"岗位。

---

## Q1. 你的 Agent 是怎么编排的？为什么不用简单 prompt？

**技术细节**：用 LangChain 实验性 `create_agent` 配 `MemorySaver` checkpoint + `recursion_limit`（默认 8 步）。定义了 5 个 `@tool`：订单查询、退款查询、故障诊断、FAQ 检索、收尾。LLM 自主决定调用顺序，而非硬编码 if-else。

**难点**：ReAct 循环可能无限递归 / 工具结果格式不稳定 / 多步后上下文膨胀。

**我的表述**："我希望让模型根据用户输入自主选择工具，所以用了 ReAct 范式。为了控制成本与爆炸半径，设了 `recursion_limit` 截断，并用结构化标签 `[INTENT:][SOURCE:]` 让模型在自由文本外额外输出机器可读元数据，前端可视化和管理统计都依赖它。"

**选型考虑**：LangChain 提供标准化 tool/agent 抽象与流式事件流（`astream_events v2`），避免自己写循环；但 `create_agent` 是实验 API，需锁定版本。

## Q2. 流式是怎么做的？前端怎么渲染工具调用？

**技术细节**：后端 `agent.astream_events(api_version="v2")` 解析 LangChain 事件，`on_chat_model_stream`→token、`on_tool_start/end`→工具轨迹，逐条 `yield` SSE。前端 `utils/sse.ts` 的 `parseSSEStream` 把事件分派给 chatStore：`onToken` 累加打字机、`onToolEnd` 渲染工具进度、`onDone` 刷新真实数据。

**难点**：SSE 断连、事件格式脆弱、弱网下体验。

**我的表述**："我做了双通道——优先 SSE 流式，一旦失败自动降级到非流式 `POST /api/chat` 拿完整 JSON，保证弱网可用。这是从真实工程痛点出发的设计。"

**选型考虑**：SSE 比 WebSocket 更轻、天然契合 HTTP 网关；但需要注意事件解析的健壮性。

## Q3. RAG 是怎么做的？检索效果如何？

**⚠️ 诚实回答点（关键）**：向量库用的是 FAISS，但编码是**字符级 numpy 哈希**（`np.frombuffer(text.encode(), uint8)`），不是语义 embedding。这是为了**离线零成本演示** RAG 全流程。

**我的表述**："原型阶段为了不依赖外部 embedding 服务、能开箱即跑，我用 FAISS + 字符哈希做了可替换的检索组件。它演示了 RAG 的『检索→注入上下文』链路，但真实语义检索应换 sentence-transformers 或云端 embeddings。我把检索层设计成独立 `VectorStore` 类，替换编码方式不影响上层。"

**选型考虑**：不隐瞒这是 demo 级检索；强调"组件可替换"体现架构意识——这比硬吹语义效果更可信。

## Q4. 怎么保证安全？怎么处理转人工？

**技术细节**：`guardrails.py` 三级——输入注入检测（中英文 BLOCK/WARN）、内容安全（危险内容 BLOCK 并触发转人工话术）、输出净化（剥离泄露的 system prompt/特殊 token）。`need_human` 由 Agent 结构化标签或安全模块判定。

**难点**：正则无法防语义越狱。

**我的表述**："我做了最小可行安全层：输入校验 + 内容安全 + 输出净化三层，中英文双覆盖。对于明显攻击用正则拦截，对于转人工场景用业务标签。我知道正则不够，生产环境会叠一层语义审核模型——但原型里我先保证链路完整、可审计。"

---

## Q5. 记忆系统怎么设计？

**技术细节**：短期用消息窗口（`MEMORY_WINDOW`）+ 超阈值时 LLM 摘要（`memory.py`）；长期用户记忆在会话关闭时抽取（`user_context.py.extract_memories_from_session`）；跨会话画像聚合（`update_user_profile`）注入系统提示。

**我的表述**："我分层管理：短期靠滑动窗口避免上下文爆炸，长期靠会话级摘要 + 用户级记忆与画像。转人工率高的用户会在下次对话被特别提示详细解答——这是从真实客服运营里借鉴的策略。"

---

## Q6. 业务数据怎么接？架构怎么做到可扩展？

**技术细节**：`services/base.py` 用 `@runtime_checkable Protocol` 定义三个服务接口；`services/__init__.py` 按 `DATA_SOURCE` 选 mock/real，real 缺失自动降级 mock。Agent 工具只依赖接口。

**我的表述**："我用了面向接口编程 + 工厂选择 + 降级。Agent 完全不感知数据来自 mock 还是真实后端，切换只需实现 `real_service.py` 并改环境变量，工具代码零改动。这是依赖倒置的体现。"

---

## Q7. 可观测性怎么做？（管理后台）

**技术细节**：每次工具调用写 `tool_calls` 表（含 `duration_ms`、`success`）；`/analytics` 聚合意图分布、来源占比、转人工率、工具耗时；`/tool-audit` 给审计明细。前端 ECharts 可视化。

**我的表述**："我把 Agent 当成一个需要被监控的系统：工具耗时、成功率、意图分布、转人工率都能从仪表盘看到。这对排查『为什么这次答得慢/答错』很关键，也方便后续做成本优化。"

## 面试红线提醒

- 被问"这是真实业务还是 demo？"→ **主动说：教学/原型项目，mock 数据验证 Agent 范式，架构按可生产化设计（服务抽象/审计/Guardrails 已具备），real_service 留口但未实现。**
- 被问"QPS/并发/测试覆盖率？"→ 诚实：原型的单 SQLite + 单连接，未做压测；零测试是已知短板，已在改进计划里。
- 被问"embedding 模型？"→ 见 Q3，不编造语义检索效果。
