# 3. 关键模块拆解

挑 5 个最核心模块，讲清"做什么 / 怎么做 / 为什么"。

---

## 3.1 Agent 编排模块 `app/agent.py`（697 行，项目灵魂）

**做什么**：构建 ReAct Agent，让 LLM 自主决定调用哪个业务工具，并产出结构化元结果（intent/source/confidence/need_human）。

**怎么做**：
- 工具定义：`query_order` / `check_refund` / `troubleshoot` / `search_faq` / `finish` 五个 `@tool` 函数（L 中段），其中 `finish` 是无副作用的"收尾"工具。
- Agent 构造用 **LangChain 实验性 `create_agent`**（非旧版 `create_react_agent`），配 `MemorySaver` checkpoint + `recursion_limit=MAX_ITERATIONS`（`config.py`，默认 8）。
- 多模型路由 `_route_model(intent, context)`：非 FAQ 类走主模型（DeepSeek），FAQ 类走 `LIGHT_MODEL`（如 mini 模型）省 token——**成本/延迟权衡的聪明设计**（agent.py `_route_model`）。
- 流式：`generate_response_stream()` 用 `agent.astream_events(api_version="v2")` 解析 LangChain v2 事件流，把 `on_chat_model_stream`/`on_tool_start`/`on_tool_end` 转成 SSE 事件。
- `parse_agent_output()` 正则从最终 AIMessage 抽取 `[INTENT:...][SOURCE:...][CONFIDENCE:...][NEED_HUMAN:...]` 标签，失败回退默认 `faq/unknown/0.5/false`。

**为什么这么做**：把"决策"交给 LLM 而非硬编码 if-else；用结构化标签解耦"自然语言回复"与"机器可读元数据"，方便前端可视化与后端 analytics 聚合。SSE v2 事件流是目前 LangChain 推荐的流式方案，比手动 token 拼接更稳。

## 3.2 向量检索模块 `app/vector_store.py`（FAISS）

**做什么**：FAQ 语义检索，支撑 RAG。

**怎么做**：
- 依赖 `faiss-cpu` + `numpy` + `httpx`（调用 DashScope OpenAI 兼容 embedding 接口）。
- `_encode(text)` 调用 **DashScope `text-embedding-v3`** 生成真实语义向量（L30-88）；若 embedding key 缺失/调用失败，自动**回退关键词（jieba 分词 + 字符重叠）检索**（L90-135），保证离线可跑。
- 索引用 FAISS `IndexFlatIP`（内积 = 余弦相似度，向量已 L2 归一化）；`_texts`/`_ids` 列表做 ID↔文本映射。
- `add_texts()` / `search(query, top_k=5)` 接口清晰；并提供 `save()`/`load()` 方法（当前未默认启用持久化）。

**为什么这么做**：用真实语义 embedding 保证检索质量，同时以"关键词回退"优雅降级，避免无 key 时系统不可用。这是比"字符哈希"更工程化的 RAG 检索实现。

> ✅ 与 README（"FAISS + DashScope"）一致。初版报告曾误判为字符哈希，已撤销（见核实清单）。

## 3.3 记忆与用户上下文模块 `app/memory.py` + `app/user_context.py`

**做什么**：短期消息窗口 + 长期用户记忆 + 跨会话画像，注入系统提示做个性化。

**怎么做**（`memory.py`）：
- `build_chat_history()`：历史 ≤ `MEMORY_WINDOW` 全用，超 `SUMMARY_THRESHOLD` 则前置 summary + 最近窗口（`memory.py` L26-51）。
- `summarize_history()`：用 LLM（复用主模型，`temperature=0`）把旧对话压成要点；失败回退拼接前 5 条用户消息（`memory.py` L54-77）。

**怎么做**（`user_context.py`）：
- `extract_memories_from_session()`：会话关闭时从 bot 消息意图 + 转人工状态抽取记忆写入 `user_memories` 表（L49-111）。
- `update_user_profile()`：聚合会话数/转人工率/Top 意图/均分，存 `user_profiles.profile_data` JSON（L118-180）。
- `get_user_context()`：把画像 + 近期记忆拼成中文提示串，注入 system prompt（L202-239）。

**为什么这么做**：体现"记忆分层"最佳实践（短期窗口 + 长期抽取 + 画像聚合）。`transfer_rate > 0.3` 时额外提示"该用户转人工频繁，请详细解答"——细粒度个性化，是真实产品里常见的运营策略。

## 3.4 Guardrails 模块 `app/guardrails.py`

**做什么**：输入校验、内容安全、输出净化三层防护。

**怎么做**：
- `validate_input()`（L72）：空/超长拒；`INJECTION_PATTERNS_BLOCK`（中英文忽略指令/角色劫持/泄露 prompt/特殊 token）命中即拒；`WARN` 级仅日志放行。
- `check_content_safety()`（L99）：`UNSAFE_PATTERNS_BLOCK`（炸弹/CSAM 等）命中 → 拒并触发转人工话术；`WARN`（自残/网络犯罪）仅日志。
- `sanitize_output()`（L119）：正则剥离泄露的 system prompt / 特殊 token / ChatML 标签，防止 prompt 泄漏。

**为什么这么做**：三级 severity（BLOCK/WARN/SAFE）+ 中英文双覆盖 + 输出净化，是 LLM 应用最小可行安全层。注意它**不做语义级越狱检测**，纯正则——对真实攻击远远不够，但对原型足够且透明。

## 3.5 服务抽象层 `app/services/*`

**做什么**：业务数据访问的接口与 mock 实现，隔离 Agent 与真实后端。

**怎么做**（`base.py`）：`@runtime_checkable Protocol` 定义 `OrderService`/`RefundService`/`TroubleshootService` 三接口，方法/返回结构/docstring 完整（`base.py` L11-58）。

**怎么做**（`__init__.py`）：按 `DATA_SOURCE` 选 `Real*`（需自行实现 `real_service.py`）或 `Mock*`；real 缺失则 try/except 降级 mock（L18-53）。

**mock_service.py**：硬编码 `MOCK_ORDERS`/`MOCK_REFUNDS`/`TROUBLESHOOT_SOLUTIONS` 字典，方法签名与 Protocol 完全一致（L114-161）。

**为什么这么做**：Protocol + 工厂选择 + 降级，是教科书级的**可插拔数据源**设计。面试里这是可重点讲的"面向接口编程 / 依赖倒置"实例。真实接入只需补 `real_service.py`，Agent 与工具代码零改动。
